# GitHub REST identity versus Copilot billing payer

Checked against GitHub's primary REST documentation on 2026-09-29. This is a documentation review, **not a live credential or billing test**. See also [the broader usage-API notes](copilot-codex-usage-apis.md).

## Conclusion

For a **fine-grained PAT** with user **Plan: read**, or a **GitHub App user access token** granted that permission, `GET https://api.github.com/user` is a supported way to obtain the authenticated personal account's `login`. GitHub explicitly lists both token types, says the fine-grained token needs **no permission for `/user` itself**, and shows `login` in its response. Thus Plan: read is required by the _subsequent personal billing report_, not by identity lookup. A successful `/user` lookup identifies the token's user; it **does not identify who pays for that user's Copilot seat**. [Get the authenticated user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user) · [Personal premium-request billing report](https://docs.github.com/en/rest/billing/usage#get-billing-premium-request-usage-report-for-a-user).

Use that `login` as the `username` path parameter of `GET /users/{username}/settings/billing/premium_request/usage` **only for the same user's personally purchased Copilot plan**, subject to authorization and availability. This avoids guessing a username; it does **not** establish that the user bought such a plan or that a report contains all their Copilot activity. GitHub explicitly limits user-level billing reports to usage **billed directly to the personal account**; organization- or enterprise-managed/billed usage is omitted and must be sought at the applicable payer level. The personal endpoint documents user **Plan: read**, GitHub App _user_ tokens and fine-grained PATs (not installation tokens), a `username` parameter, and 403/404 possibilities. Its `usageItems` are historical billed usage, **not remaining quota**. [Billing usage introduction and user report](https://docs.github.com/en/rest/billing/usage#get-billing-premium-request-usage-report-for-a-user).

| GitHub App **user** access token         | Supported; no additional `/user` permission.                                                                                                                                                         | Documented with user **Plan: read**.                                                                                                                                                                                                                      | Separately documented with organization **Administration: read** and administrator access.                                                                |
| GitHub App **installation** access token | **Not listed** among `/user`'s supported token types: app installation is not an authenticated human identity for this operation.                                                                    | **Not listed** for the user report.                                                                                                                                                                                                                       | Listed for the organization report when the app has organization **Administration: read** and meets its access conditions; the org path must be supplied. |
| Classic PAT                              | `/user` identifies its owner. GitHub says `read:user` or `user` is needed for the **private** user response; tokens without those scopes get the **public** user response, which also shows `login`. | The billing endpoint does **not document a classic-PAT scope** (its Plan: read statement applies to fine-grained tokens). Sources: [GitHub REST `/user` reference](https://docs.github.com/en/rest/users/users#get-the-authenticated-user), [personal and organization premium-request billing references](https://docs.github.com/en/rest/billing/usage), [REST authentication and classic/fine-grained distinctions](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api). GitHub lists 401/403 for `/user`; treat failed identity lookup as an error, **not** a cue to substitute a configured or guessed account.

## Why membership is not payer discovery

`GET /user/orgs` reports organizations the authenticated user may operate on, **not which organization pays for a Copilot license**. More strongly, GitHub expressly states that requests with a **fine-grained access token return HTTP 200 with an empty list**: an empty list here cannot prove there is no org payer. Classic PATs/OAuth tokens need at least `user` or `read:org` for this endpoint, and results depend on authorization; `/users/{username}/orgs` exposes only _public_ memberships. None of these responses identifies a payer. [List organizations for the authenticated user; list organizations for a user](https://docs.github.com/en/rest/orgs/orgs#list-organizations-for-the-authenticated-user).

With a **known, authorized** organization, an organization owner can query `GET /orgs/{org}/members/{username}/copilot` to verify that organization's Copilot seat assignment (public-preview API, org-specific permissions), or its billed seat list; these are not a token-wide payer-discovery operation. The payer-specific usage endpoint is `GET /organizations/{org}/settings/billing/premium_request/usage`, which requires organization-administrator access and organization **Administration: read** for the documented fine-grained tokens. Organization membership alone is insufficient to select this path; enterprise billing can require the enterprise-level report instead. Require explicit payer selection/independent confirmation and authorization; never pick the first org or silently treat personal usage as total usage. [Copilot seat assignment](https://docs.github.com/en/rest/copilot/copilot-user-management#get-copilot-seat-assignment-details-for-a-user) · [Organization billing and billing-level distinction](https://docs.github.com/en/rest/billing/usage#get-billing-premium-request-usage-report-for-an-organization).

**Limits:** No token, org membership, SSO, purchased subscription, permission enforcement, actual API response, or payer was tested with live credentials. The references specify supported token types and expected permission gates; they do not guarantee a particular account's billing eligibility or establish a universal classic-PAT scope for these newer billing endpoints.
