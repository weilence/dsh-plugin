# GitHub Copilot and OpenAI Codex subscription usage interfaces

Verified against live first-party documentation on **2026-09-29** (local date; vendor docs and plans change). “Programmatic” distinguishes a documented, supported API from an interactive CLI display or a private backend endpoint. No account credentials were used to test responses.

## Verdict at a glance

| Scope                                | Documented machine-readable path                                                                                                                                                                           | What it actually measures                                                                                                                         | Can it show live remaining subscription quota?                                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| GitHub Copilot, organization-billed  | [GitHub Billing Usage REST](https://docs.github.com/en/rest/billing/usage#get-billing-premium-request-usage-report-for-an-organization): `GET /organizations/{org}/settings/billing/premium_request/usage` | Billed premium-request usage, historical quantities/amounts, optionally filtered by `user`, date, model and product                               | **No:** historical billing report, not current per-seat remaining allowance; admin rights required.                                 |
| GitHub Copilot, personally purchased | [GitHub Billing Usage REST](https://docs.github.com/en/rest/billing/usage#get-billing-premium-request-usage-report-for-a-user): `GET /users/{username}/settings/billing/premium_request/usage`             | Premium-request usage billed **directly to the personal account**                                                                                 | **No:** excludes a user's organization/enterprise-billed license and does not return session/weekly remaining quota.                |
| GitHub Copilot, org seat             | [Copilot user-management REST](https://docs.github.com/en/rest/copilot/copilot-user-management#get-copilot-seat-assignment-details-for-a-user): `GET /orgs/{org}/members/{username}/copilot`               | Assignment, plan and last activity; endpoint response label says “including usage,” but its shown schema does not include remaining premium quota | **No**; seat inventory is not a quota balance.                                                                                      |

## GitHub: billing versus seat entitlements

- The two [premium-request billing report endpoints](https://docs.github.com/en/rest/billing/usage) are **documented GitHub REST APIs**. Organization path: `GET https://api.github.com/organizations/ORG/settings/billing/premium_request/usage`; GitHub specifies an organization administrator and a fine-grained GitHub App user/installation token or fine-grained PAT with organization **Administration: read**. Personal path: `GET https://api.github.com/users/USERNAME/settings/billing/premium_request/usage`; fine-grained GitHub App user token or fine-grained PAT with user **Plan: read**. Both show `usageItems`, including `grossQuantity`, `netQuantity`, `grossAmount`, `netAmount`, `unitType`, `sku`, and model, with up to 24 months accessible. Choose an [explicit GitHub REST API version](https://docs.github.com/en/rest/about-the-rest-api/api-versions); the live examples currently use `2026-03-10`. [Source: official billing endpoint reference](https://docs.github.com/en/rest/billing/usage).
- **Authenticated identity is not the payer:** GitHub's [GET /user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user) returns the token holder's `login` with a fine-grained PAT or GitHub App user token and requires no extra fine-grained permission. A client can validate this login and use the personal billing endpoint without asking the user to enter a username. This only identifies the account behind the **personal** report; [organization membership](https://docs.github.com/en/rest/orgs/orgs#list-organizations-for-the-authenticated-user) does not identify which organization pays for Copilot. Organization billing still requires an explicit payer.
- **Do not omit the personal endpoint**: the same reference explicitly says user reports only include Copilot usage paid for by a user's _own_ plan; an organization/enterprise-billed seat's activity must be queried at its paying organization/enterprise level. Nor does an org admin necessarily get per-user analytics via the `user` API filter: [GitHub's monitoring guide](https://docs.github.com/en/copilot/how-tos/manage-and-track-spending/monitor-premium-requests) says organization owners cannot view premium-request analytics by user or use `user` in the API; enterprise owners/billing managers can, and org owners should use downloadable usage reports for user-level detail. Permissions and availability must be checked against the specific billing account.
- [Copilot seat REST](https://docs.github.com/en/rest/copilot/copilot-user-management) provides `GET /orgs/{org}/copilot/billing`, `/billing/seats` and `/orgs/{org}/members/{username}/copilot`, with owner/permission gates and **public-preview** status on that page. These expose seat counts/assignment/last activity, not a documented live quota snapshot. [GitHub's monitoring guide](https://docs.github.com/en/copilot/how-tos/manage-and-track-spending/monitor-premium-requests) points individuals at IDEs, GitHub.com billing and Copilot CLI UI; monthly premium-request counters reset at 00:00 UTC on the 1st, but GitHub also describes **session and weekly limits** for Pro/Pro+/student beginning April 20, 2026. Therefore “monthly premium requests consumed” must not be conflated with all usable remaining capacity. Current pricing/billing terminology also includes [AI credits](https://docs.github.com/en/rest/billing/usage#get-billing-ai-credit-usage-report-for-a-user), so re-check the exact SKU and plan rather than hard-coding a universal request model.
- **Copilot CLI private endpoint:** A proposed `https://api.github.com/copilot_internal/user` direct-polling path is **not** one of the published [GitHub Billing REST methods](https://docs.github.com/en/rest/billing/usage) or [Copilot REST methods](https://docs.github.com/en/rest/copilot). We did **not** validate the path's current payload or its use by a specific CLI release from published first-party source code, so it must not be presented as an official API, asserted to accept ordinary GitHub REST PATs, or used to promise a stable personal seat quota. The [official Copilot CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) describes browser/device OAuth, credential-store fallback and `COPILOT_GITHUB_TOKEN`/`GH_TOKEN`/`GITHUB_TOKEN` token precedence; its supported PAT mode requires a fine-grained **Copilot Requests** permission (classic PATs unsupported). A CLI token's scopes and audience are **not** automatically equivalent to Billing REST authorization. Calling private endpoints by extracting/replaying CLI credentials crosses a separate security and compatibility boundary.

## OpenAI: separate ledgers and a supported local integration

- [OpenAI Usage API](https://platform.openai.com/docs/api-reference/usage) defines organization-level `GET https://api.openai.com/v1/organization/usage/completions` (time buckets, request count, input/output/cached tokens, optional `group_by` model/project/user/API key) and `GET /v1/organization/costs` (monetary cost, project/line item). Its request examples use an **`OPENAI_ADMIN_KEY`**. OpenAI advises Costs for invoice reconciliation because Usage and Costs can differ. [OpenAI's billing help](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform) explicitly separates ChatGPT billing from API Platform billing. [Codex auth](https://developers.openai.com/codex/auth) says ChatGPT login draws on subscription access, whereas API-key Codex usage is charged at standard API rates; API organization usage/cost APIs therefore **cannot** monitor ChatGPT/Codex included allowance.
- [Codex pricing/limits](https://developers.openai.com/codex/pricing) says consumption depends on model/task size, with shared five-hour local/cloud windows and possible weekly limits; it points to the **Codex usage dashboard** and CLI `/status` for remaining limits. [Codex CLI slash-command reference](https://developers.openai.com/codex/cli/slash-commands) additionally documents `/usage daily|weekly|cumulative` for token activity, while `/status` shows session/token/context details. `codex login status` reports **authentication status**, not a documented standalone quota JSON API ([authentication guide](https://developers.openai.com/codex/auth)). Do not scrape these human-readable TUI outputs as an API.
- **Positive answer for Codex subscription:** OpenAI [documents `codex app-server`](https://developers.openai.com/codex/app-server), a versioned-by-installed-binary _local_ JSON-RPC 2.0 protocol (default JSONL over stdio): start it, send `initialize` then `initialized`, and call `account/read` for login mode/plan, `account/rateLimits/read` for current ChatGPT rate limits, or subscribe to `account/rateLimits/updated`. The rate-limit response has backward-compatible `rateLimits` plus optional `rateLimitsByLimitId`; each bucket can include `usedPercent`, `windowDurationMins`, Unix-second `resetsAt`, `limitId`, `rateLimitReachedType`, `planType`, and available credits. `account/usage/read` returns ChatGPT **token-activity** `summary` and optional `dailyUsageBuckets`, **not** a quota remaining value; it requires Codex-service-backed auth (ChatGPT or supported service identity; API-key-only and Bedrock authentication do not qualify). Null/absent fields and multiple buckets are explicitly part of the documented contract. Generate schemas from the installed binary using `codex app-server generate-ts`/`generate-json-schema` and confirm that release supports the methods; live docs are not a guarantee about an older local executable. [Source: official app-server protocol and account API examples](https://developers.openai.com/codex/app-server).
- [OpenAI's Codex auth guide](https://developers.openai.com/codex/auth) documents browser/device ChatGPT login and separate API-key login; the former's cached secrets may reside in `~/.codex/auth.json` **in plaintext** or an OS credential store, with automatic token refresh. Use Codex-managed login if adopting app-server; never read another tool's credential cache opportunistically. [App-server auth docs](https://developers.openai.com/codex/app-server) describe `chatgptAuthTokens` as **experimental**, requiring `experimentalApi`, a host-provided access token/account ID, and a host callback to refresh tokens on 401 within roughly 10 seconds; only use where the host **owns** that complete token lifecycle. `codex app-server --listen ws://...` is itself experimental/unsupported and potentially unauthenticated on non-loopback by default: prefer stdio and avoid exposing auth-bearing RPCs over a network ([transport/security docs](https://developers.openai.com/codex/app-server)).
- **Private OpenAI endpoint, now verified from first-party source:** [OpenAI's Codex backend client](https://github.com/openai/codex/blob/4994306e9f80448bde85e770a0b0c93d3fee5665/codex-rs/backend-client/src/client/rate_limit_resets.rs#L69-L80) GETs `https://chatgpt.com/backend-api/wham/usage` with ChatGPT OAuth access and a matching account ID where available. This removes the **binary** prerequisite for a consumer that already owns usable ChatGPT OAuth credentials, but does not turn that endpoint into a documented public third-party API. Authentication, wire shape and rate limits may change. See the [pinned-source analysis and credential-ownership caveat](codex-direct-usage.md).

## Practical choice and limitations

1. For historical GitHub spend, use the **documented payer-specific** GitHub billing REST path with the exact least-privilege permission; show billed period, account, and “historical usage,” not “remaining quota.” If the seat is org-funded, a personal billing response is not authoritative.
2. For ChatGPT-managed Codex _live_ rate-limit indicators, the **documented app-server `account/rateLimits/read`** works when Codex is installed and logged in. A binary-free alternative is a Host-only GET to the **undocumented** endpoint verified above, using the existing DSH `openai-codex` OAuth grant, provided the implementer accepts both endpoint and credential-payload coupling. `account/usage/read` describes token activity, not quota.
3. Keep OAuth and credential ownership explicit: do not repurpose Copilot CLI or Codex credential files, do not log tokens, and do not give browser clients bearer credentials. DSH's `llm-pi-ai` owns the grant and atomic refresh; because it currently exposes no owner-side subscription-usage method, direct access from `dsh-models` is an explicit compatibility trade-off, not an established cross-plugin interface. If such an owner-side method becomes available, prefer it over interpreting another plugin's opaque payload.

**Evidence boundary:** Supported contracts above come from official documentation; the private Codex endpoint and schema come from pinned first-party source code, not a live authenticated request. Real subscription credentials, server-enforced header requirements, SKU availability, and older CLI behavior were not tested.
